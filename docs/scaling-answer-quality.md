# Maintaining Answer Quality at Tens of Thousands of Documents

Growing from a small in-memory library to tens of thousands of insurance documents changes the main risk from “can we retrieve anything?” to “can we reliably retrieve the right version and the right passage?” I would preserve the current separation between retrieval, grounding, generation, and citation construction, but replace each simplistic retrieval choice with an evaluated one.

First, I would move vectors to a persistent approximate-nearest-neighbor index such as pgvector, Chroma, or another operationally supported store. Every chunk would retain filterable metadata: tenant or business unit, policy type, jurisdiction, product, effective dates, document version, language, and ingestion status. Query-time metadata filtering should narrow the candidate set before semantic ranking. This prevents a semantically similar but obsolete or wrong-jurisdiction policy from outranking the applicable source. Document hashes and stable version identifiers would prevent duplicate ingestion and allow superseded versions to be excluded without destroying their audit history.

Chunking would remain deliberately simple until evaluation shows a problem, but it would become structure-aware. Headings, sections, clauses, tables, and page boundaries are better units than arbitrary windows. The selected embedding model's tokenizer would enforce token limits, with moderate overlap retained where a clause crosses a boundary. I would compare several chunk sizes rather than assume one universal setting: small chunks often improve pinpoint retrieval but lose necessary qualifications, while large chunks retain context but reduce embedding specificity and consume more prompt tokens.

Retrieval would likely become a two-stage pipeline. A first stage would combine semantic vector search with lexical/BM25 search because insurance questions often contain exact policy numbers, exclusions, defined terms, or statutory language that dense embeddings may underweight. Reciprocal-rank fusion could merge those candidate lists. A reranker would then score perhaps the best 20–50 candidates and select a smaller, diverse context set for generation. Top-K should be tuned alongside chunk size and reranking; simply increasing K can lower answer quality by adding distracting passages.

The weak-match gate remains essential. Similarity-score distributions change when the embedding model, index, or corpus changes, so the current threshold cannot be copied blindly. I would build a small labeled evaluation set containing answerable questions, unanswerable questions, ambiguous questions, and questions whose answer exists only in an obsolete version. Offline metrics would include recall@K, mean reciprocal rank, no-answer precision/recall, citation correctness, and grounded-answer faithfulness. Thresholds and retrieval parameters would be selected from those results, then monitored on anonymized production traces with explicit user feedback. A model or index migration would run the same evaluation before release.

Finally, generation must not compensate for weak retrieval. If no candidate passes the calibrated gate, the service should continue returning an explicit insufficient-information answer without calling the LLM. For accepted context, the prompt should remain context-only, and citations should still be constructed from backend metadata. At greater scale I would add structured claim-to-source output, validate every referenced source against the retrieved set, and reject unsupported claims. Observability should record retrieval scores, applied filters, selected versions, latency, token use, and citation coverage—without logging sensitive policy text by default. These controls improve quality by making retrieval failures measurable and keeping the model downstream of an auditable evidence-selection process.
